### The rule

Every change is one *command*, run by one *executor*. A command either did not
run (nothing changed, nothing recorded) or completed (every write and its audit
row committed together). There is no state in between.

### Decisions

1. **Bulk operations run one command per row.** Ticking twenty users and
   pressing Disable runs twenty commands; each succeeds or is refused on its
   own, and the page lists the refusals, as today.
2. **No audit, no change.** The audit row is written inside the command's
   transaction. If it cannot be written, the whole command rolls back. A broken
   audit table therefore stops all administrative changes; that is accepted.
3. **Converted in one go**, not incrementally: every command below moves to the
   executor in one piece of work, and the old direct paths are removed.

4. **Each transaction is a type; one enum lists them all.** Required parameters
   are plain fields, optional ones `Option<T>`; the compiler enforces both, so no
   annotations. Each has its own result type.
5. **One engine runs them, through a context.** A transaction aborts only by
   asking the context to fail with an error; it cannot abort without one.
6. **Batches share one context and one commit.** Several transactions can run as
   a batch: nothing commits until the last succeeds, and any abort rolls back the
   whole batch.
7. **A transaction takes its own locks**, never deadlocks, and gives up after a
   timeout, failing cleanly.
8. *(My default, not yet confirmed)* The per-kind table (action, scope, audit
   event, name) is generated by a declarative `macro_rules!` list rather than a
   proc-macro derive, to avoid a separate crate.
9. *(Unchanged from 1)* The console's bulk buttons stay one transaction per row;
   batches are the explicit tool for CLI scripts and composite actions.

### Shape

```rust
/// One transaction: its parameters are its fields.
pub struct CreateUser {
    pub tenant: TenantId,              // required: a plain type
    pub upn: Upn,
    pub password: PasswordHash,        // hashed before the transaction begins
    pub display_name: Option<String>,  // optional: Option<T>
    pub require_change: bool,
}

pub trait Transaction {
    type Output;                       // its result type
    const KIND: TxnKind;               // action, scope, audit event, name
    async fn run(&self, cx: &mut Cx) -> Step<Self::Output>;
    /// The audit row for a completed run: never a secret, never an unresolved
    /// identifier (see the audit hygiene rules).
    fn audit(&self, out: &Self::Output) -> AuditEntry;
}

/// Every transaction there is.
pub enum Txn { CreateUser(CreateUser), ResetMfa(ResetMfa), /* … */ }

/// The only way to abort is `cx.fail(error)`: nothing else can build one.
pub struct Aborted(/* private */);
pub type Step<T> = Result<T, Aborted>;

impl Cx {
    pub fn fail(&mut self, e: Refusal) -> Aborted;     // records the error
    pub fn actor(&self) -> &Actor;
    pub fn db(&mut self) -> &mut DbTransaction;
    pub async fn lock(&mut self, what: LockTarget) -> Step<()>;  // see Locking
}

/// The standard result of every run.
pub enum Outcome<T> {
    Done { output: T, audit_id: AuditId },  // committed
    Refused(Refusal),                       // rolled back: the actor can fix it
    Failed(Internal),                       // rolled back: our fault, or contention
}

pub enum Refusal {
    NotPermitted,
    NotFound(What),
    Invalid(String),
    Conflict(String),
    RuleBroken(Rule),      // a global invariant would not hold
    Busy(LockTarget),      // a lock was not granted in time; safe to try again
}
```

### The engine

`engine.run(actor, txn) -> Outcome<T>` and
`engine.run_batch(actor, Vec<Txn>) -> BatchOutcome`:

1. Authorize each transaction for the actor (console session or CLI); for the
   console, check CSRF.
2. Begin one database transaction, with the lock timeout set (see Locking).
3. Run each transaction in order with the same context. The first abort stops
   the batch.
4. Check the global invariants once, at the end, against the final state:
   - at least one live, enabled root-tenant account can act as Global Administrator;
   - every role binding has the scope its role and holder allow;
   - no application that accepts only its own tenant has outside assignments.

   Intermediate states inside a batch may break them (grant Bea, then revoke
   Alice, works even when Alice is the only one).
5. Write one audit row per transaction, sharing a batch id.
6. Commit if everything succeeded; otherwise roll back, audit rows included.

`BatchOutcome` holds every output on success, or the position and refusal of
the transaction that aborted.

Every console page turns an `Outcome` into a response one way (done: redirect;
refused: the page with the message, or 403/404; failed: 500); the CLI turns it
into a message and an exit code.

### Locking

- **Each transaction locks what it reads for its checks**, through `cx.lock`:
  `SELECT … FOR UPDATE` on Postgres and MySQL; on SQLite the transaction began
  with `BEGIN IMMEDIATE`, which already holds the database, so row locks are no-ops.
- **Rules that span many rows lock a named row** in a small locks table: every
  transaction touching role grants locks `role_bindings`, which serialises them
  and closes the concurrent last-Global-Administrator race.
- **No deadlocks, by a fixed order.** Every lock target has a rank (named locks,
  then tenant, user, group, application, then everything else by id). `cx.lock`
  refuses a lock of lower rank than one already held: that is a programming
  error, reported as `Failed` and caught by tests, never a deadlock in production.
- **Every wait has a timeout.** Postgres `SET LOCAL lock_timeout`, MySQL
  `innodb_lock_wait_timeout` for the session, SQLite's busy timeout for
  `BEGIN IMMEDIATE`. Default 5 seconds. A lock not granted in time aborts with
  `Refused(Busy)` and the whole transaction or batch rolls back; nothing waits
  forever. A deadlock the database detects anyway (a backstop) is reported the
  same way.
- **Locks end with the transaction**: released at commit or rollback, and a
  transaction dropped on any error path rolls back, so no lock outlives its run.
  A lock taken early in a batch is held until the batch ends.
- **Nothing slow inside**: password hashing, key generation and any HTTP call
  happen before the transaction begins.
- The key-rotation lock (migration 0008) becomes a named lock of the engine.

### Testing

- Each transaction runs through the engine against a test database with no
  HTTP: `engine.run(actor, CreateUser { … })`, asserting on the `Outcome`.
- One test walks every `TxnKind`: each has an authorization, a distinct audit
  event and at least one refusal test.
- Locking: a lock taken out of order fails; a lock held by another connection
  times out as `Busy` and changes nothing.

### Gaps this closes (known today)

1. Application *Sign-in and grants* saves up to four settings in separate writes;
   a failure part-way leaves some saved.
2. Creating a user in the console with *require change* is two writes.
3. *Reset MFA* removes the authenticator in one transaction and ends sessions in
   another.
4. Turning *Accept accounts of other tenants* off checks for outside assignments
   and updates in separate statements; a concurrent assignment can slip between.
5. The last-Global-Administrator rule can be beaten on Postgres at the default
   isolation level by two concurrent removals (write skew).
6. Audit rows are written after the change commits, and a failed audit write is
   only logged (`routes/audit.rs`), leaving an unaudited change.

**Command line**: bootstrap; tenant create, change-domain; user create,

**Out of scope**: sign-in bookkeeping (failed-attempt counters, lockout,
sessions, MFA tickets, codes and tokens). These are not administrative changes
and keep their own handling.
